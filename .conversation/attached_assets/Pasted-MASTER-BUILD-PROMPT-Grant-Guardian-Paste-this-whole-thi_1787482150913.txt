Project Identity

Name: Grant Guardian One-liner: An autonomous AI agent that protects researchers from two silent risks — citing retracted/corrected papers, and missing compliance deadlines — by handling both in the background and only surfacing genuine judgment calls.

Built for: Agents for Humans Hackathon (agentsforhumans.devpost.com), sponsored by AWS, run on Devpost. Track: Professional Agents Required tech: Strands Agents SDK (Python) — non-negotiable, this is the hackathon's core requirement. Deadline: September 14, 2026, 5:00pm PDT.

The Problem (use this framing in all copy — README, video script, pitch)

Researchers — especially solo researchers, grad students, and small labs without dedicated admin support — carry two invisible risks nobody actively watches for them:

Citation rot: a paper they cited gets retracted or corrected after they cited it. They often don't find out until a reviewer, editor, or the internet points it out — sometimes after publication, which can damage credibility or force a correction of their own work.
Compliance drift: IRB renewals, funding progress reports, and other deadline-bound obligations that are easy to lose track of during a busy research cycle. Missing one can mean losing funding or research authorization entirely.

Both are exactly the kind of task described in the hackathon's own brief: "work that only a person can judge and a pile of repetitive tasks around it that shouldn't need one."

Who it's for

Solo researchers, PhD students, and small academic labs — anyone managing their own citations and compliance obligations without institutional support staff.

Why it matters

These aren't productivity nice-to-haves. A missed retraction can force a correction or retraction of the researcher's own paper. A missed compliance deadline can suspend a study or cut off funding. Grant Guardian exists so these risks get caught silently, before they become a crisis.

The Novelty Layer (this is the differentiator — build it, don't skip it)

Any competitor could build "checks if your citations are retracted." That's table stakes. Grant Guardian's edge is propagation risk detection: it doesn't just check papers you directly cited — it walks the citation graph to catch papers you cited that rely on a result which was later retracted, even when you never cited the retracted paper yourself.

Why this matters: a retraction doesn't just poison the retracted paper — it can quietly undermine every paper built on top of its findings. A researcher can do everything "right" — check their own direct citations — and still unknowingly build on compromised work one hop removed. This is the exact kind of risk "only a person can judge," which is the track's own framing, and almost no citation tool checks for it because it requires graph traversal, not a lookup.

How to build it: use the Semantic Scholar Academic Graph API (free, public, no key required for basic use) — it exposes a paper's citation and reference graph. For each directly-cited paper, pull its own references one level deep, and cross-check those against the retraction database too. Flag second-order hits with lower urgency than direct hits (these are judgment calls, not clear-cut — route them through escalation, not auto-flagging).

This is also your strongest demo moment: showing a citation that looks completely clean on a direct check, then the agent surfacing "this paper builds on a result that was retracted in 2019" is the single most impressive thing you can put on camera.

The hackathon rules don't mandate a specific platform (mobile vs. web vs. CLI) — the actual requirement is that judges can access "a website, functioning demo, or a test build." Build this as a web app (FastAPI backend + React/Next.js dashboard), not a CLI-only tool or a mobile app:

A live demo URL is explicitly called out as strengthening the Technical Implementation score
"Design" is one of five equally-weighted judging criteria — a bare terminal script reads as a proof-of-concept, not "a complete, coherent product experience," and will underscore there regardless of how good the underlying agent is
Mobile isn't required and adds build risk for no rubric benefit — skip it

Deploy the web app somewhere with a real public URL before submission (Replit Deployments, or any free-tier host) — don't submit with only localhost instructions.

Core Design Principle (repeat this constraint throughout the build)

Grant Guardian is not a chatbot. It is not a dashboard the researcher has to check. It runs autonomously in the background and only interrupts the human when a genuine judgment call exists — not for routine matches, not for clean confirmations. This distinction is the single most important thing the hackathon judges are scoring for (see Judging Criteria below), so every design decision should default toward "the agent acts" over "the agent asks."

Agent Architecture (Strands Agents SDK)

Build one orchestrating agent with the following tools. Do not build a multi-agent swarm — a single agent with a clear, traceable tool-use loop is easier to demo reliably and scores just as well on Technical Implementation, which rewards depth of correct usage, not agent count.

Tools
scan_citations(document_id) Pulls the current reference list from a tracked document (start with a manually-uploaded bibliography/BibTeX file or a static Google Doc for v1 — live Google Docs API integration is a stretch goal, not a blocker).
check_retraction_status(doi_or_title) Checks a paper against retraction/correction data. Use the Crossref API (free, no key required, has a is-retracted/related-work signal via the "updates" relation) and/or Retraction Watch's database (retractiondatabase.org has a downloadable dataset) as the source of truth. Cache results locally — don't re-check the same DOI every run. Demo dataset note: for a reliable live demo, don't rely on discovering a real retraction live — pull 3-5 known-retracted papers from the Retraction Watch database ahead of time (e.g. a well-known retracted COVID paper, a retracted psychology study) and seed a demo bibliography that mixes these with clean citations. This guarantees the "agent catches it" moment actually happens on camera instead of depending on live API luck.
flag_citation_issue(citation, issue_type, severity) Records a flagged citation. issue_type: "retracted" | "corrected" | "expression_of_concern". severity determines whether this auto-drafts a note or escalates (see escalation logic below).
track_compliance_deadline(deadline_type, due_date, requirement_details) Registers a compliance obligation (IRB renewal, funding report, etc.) with its due date.
draft_compliance_report(deadline_id) Auto-drafts the routine parts of a report (progress summary pulled from prior notes/logs, boilerplate sections) and saves it as a draft for the researcher to review — does NOT submit anything autonomously; compliance submissions always need a human signature, but the drafting labor is the part the agent removes.
escalate_to_human(reason, context, urgency) Called only when the agent cannot safely resolve something alone. Examples: an ambiguous retraction (correction vs. full retraction, unclear from source data), a compliance requirement with conflicting or missing information, a deadline inside 48 hours with no draft ready, a second-order propagation risk (see tool 7).
check_propagation_risk(doi) — the novelty tool, build this one carefully For a directly-cited paper, pulls its references one level deep via the Semantic Scholar Academic Graph API and cross-checks those against the retraction database. If a paper the researcher cited relies on a now-retracted finding, this surfaces as a second-order risk — always routed to escalate_to_human rather than auto-flagged, since judging the actual impact requires human context the agent doesn't have.
System Prompt Direction

The agent should be instructed to: act decisively on clear-cut cases (a paper is unambiguously retracted → flag and draft the note immediately), never escalate for routine matches, and always state its reasoning briefly when it takes an action (this reasoning trace is what gets logged and shown on the demo dashboard — critical for the Design and Technical Implementation scores).

Tech Stack
Agent core: Strands Agents SDK (Python), model via Amazon Bedrock (Claude). Request Bedrock model access in the AWS console on day one — approval isn't always instant, don't discover this blocker in week 3. Strands also supports other model providers as a fallback if Bedrock access is delayed.
Backend: FastAPI — serves dashboard data, exposes demo-trigger endpoints so the live demo doesn't depend on real webhook timing
Frontend: Simple React/Next.js dashboard — three panels: (1) tracked citations with flag status, (2) compliance deadline tracker, (3) agent decision log showing every autonomous action with its reasoning — this log is the single highest-leverage thing for scoring, make it prominent
Data: SQLite (don't over-engineer the data layer — judges score agent behavior, not database choice)
External APIs: Crossref API (citation/retraction metadata), Retraction Watch dataset, Semantic Scholar Academic Graph API (citation network traversal — powers the propagation risk detection)
Deployment (optional but scores-boosting): Amazon Bedrock AgentCore Runtime — wrap the agent for this after the core loop works locally, don't let it block iteration speed
Hosting for build: Replit is fine for development; keep AWS credentials in Replit Secrets, never hardcoded or committed
